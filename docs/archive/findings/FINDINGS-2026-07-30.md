## 1. Correctness — the seal that shouldn't have served

### 1.5 A forged seal cannot serve, but can still be the draft — **verified**

`engine._context_pairs` filters through `memory.verified_sealed`, with an
explicit comment: *"a forged 'sealed' row must not reach the engine's system
prompt as authoritative TM (Nestor#2 follow-up)."* `OfflineEngine.translate`
calls bare `memory.lookup()` and returns the matched row's `target_text` as the
draft.

So the hardening covers the path that contributes *style hints* and not the path
that copies attacker-controlled text *verbatim into the first thing a reviewer
reads.*

```python
# NESTOR_SEAL_KEY=realkey, forged row written directly to the store without it
s.memory_insert(dict(id="forged", source_text="the invoice total",
    source_norm=memory._norm("the invoice total"), source_lang="en",
    target_text="WIRE FUNDS TO ACCOUNT 9910", target_lang="es",
    status="sealed", verifier="mallory", weight=1.0, origin="",
    created_at=memory._now(), seal_sig="bogus"))

memory.best_sealed("the invoice total", "en", "es")   # -> None                 ✓
_context_pairs("the invoice total", "en", "es", store=s)  # -> []               ✓
OfflineEngine().translate("the invoice total", "en", "es", store=s).text
# -> 'WIRE FUNDS TO ACCOUNT 9910'                                               ✗
```

**Severity, stated honestly: this is not a serving hole.** The result is
`state='draft'`, it enters the review queue, and a human sees it before anything
is sealed. Nestor's safe state holds. It is also true that drafts are permitted
to draw on drafts — the README says so — so an argument exists that this is
working as intended.

What makes it worth an entry is that the argument is not *written down*, and the
adjacent path has the opposite decision recorded in a comment. The asymmetry
reads as an oversight rather than a choice, and the exposure is the wrong way
round: reviewers anchor hardest on the text they are shown first, so a forged
row influences the draft more than it would have influenced the system prompt it
was deliberately kept out of.

Two ways to close it, and the second is as good as the first:

- Wrap the lookup in `verified_sealed(...)`, matching `_context_pairs`.
- Leave the behavior and add a comment saying drafts-from-unverified-rows is
  intended, so the next reader does not have to re-derive whether it was.

### 1.6 A rejection can halt a bulk seed — the failure the conflict catch exists to prevent — **verified**

`seed_from_corpus` catches `ConflictingSealError` specifically so an import does
not die partway. Its docstring gives the reason: *"Letting that escape would
abort a bulk import partway and leave a half-loaded memory, so conflicts are
skipped and the rest of the corpus still lands — a curated file must not overrule
a person, and must not be able to halt the load either."*

`add_pair` raises `RejectedPairError` from the same code path, a few lines
earlier, and it is not caught.

```python
p = memory.add_pair("hello", "hola", "en", "es", status="sealed", verifier="rita")
memory.reject_pair(p["id"], verifier="rita", reason="wrong register")

def loader():
    return [{"front": "hello",   "back": "hola",  "lang_front": "en", "lang_back": "es", "lesson": "L1"},
            {"front": "goodbye", "back": "adios", "lang_front": "en", "lang_back": "es", "lesson": "L1"}]

memory.seed_from_corpus(loader=loader)
# RejectedPairError: pair 229b4a47… was rejected by 'rita' and will not be re-sealed
# pairs written: {'total': 1, 'sealed': 0, 'draft': 1}   <- 'goodbye' never reached
```

One previously rejected phrase anywhere in a corpus stops the load at that row.
The rest of the file silently does not arrive — silently in the sense that
matters, since the exception names a pair id and says nothing about the import
being incomplete.

The reasoning already written for conflicts transfers word for word: a curated
file must not overrule a person, *and must not be able to halt the load either.*
The fix is the same shape as the existing one — skip, log the skip, count it into
the warning:

```python
except (ConflictingSealError, RejectedPairError) as e:
    skipped += 1
    _log_seal_event({
        "kind": "seed_conflict" if isinstance(e, ConflictingSealError) else "seed_rejected",
        ...
    })
    return 0
```

Distinguishing the two `kind`s matters more than it looks: *"already sealed
differently by a human"* and *"previously rejected by a human"* are different
facts about the corpus, and collapsing them into one ledger entry would lose the
difference the rejection machinery exists to preserve.

## 4. Positioning

### 4.5 The README claims two things the repo already knows are not true — **verified**

Not a code defect. A documentation drift, in a project whose entire subject is
the gap between a claim and a verifiable fact — which is the only reason it is
worth an entry.

**The test count.** `README.md` says 96 tests in three places (lines 44, 149,
522). `pytest -q` on this revision reports **123 passed**. The count grew and the
prose did not. Nothing depends on it, but a reader checking whether the repo
means what it says will run the suite, and the first number they compare will not
match.

**The ledger refusal.** `README.md:370`:

> the existing chain is verified before it is extended, so a new entry can never
> launder a tampered history

`IDEAS.md` §5.3 already records that this is verified once per process. Demonstrated
again here for completeness — two honest appends, tamper line 1, append again:

```
after 2 honest appends: (True,  'intact — 2 entries')
after tamper:           (False, "broken chain at line 1: prev=… expected …")
append:                 ACCEPTED
final verify:           (False, "broken chain at line 1: …")
```

**Be precise about what is and is not lost.** The tamper is still *caught* —
`verify()` fails before and after, and the chain stays broken. Tamper-evidence,
the load-bearing property, holds completely. What does not hold is the word
**never** in the refusal-on-append promise: inside one long-lived process, after
the first append, a new entry is chained onto a tampered history without a
refusal. You lose the early refusal, not the evidence.

So the fix here is one sentence of prose, independent of whether §5.3 is ever
implemented:

> the existing chain is verified before it is first extended in a process, so a
> broken chain is refused rather than silently extended — see IDEAS.md §5.3 for
> the once-per-process limit

A repo that publishes its own false-seal rate at the shipped default should not
have a README that is stronger than its own known limitations.

## Not findings — noted because they are easy to get wrong and were not

- **`_same_verifier` refuses to treat `"" == ""` as the same actor.** `verifier`
  defaults to empty and empty is what every scripted or unauthenticated caller
  passes, so the obvious implementation waves through every anonymous re-seal —
  and would look correct in review.
- **`NumericMatcher.parse` rejects `bool` before `int`.** `isinstance(True, int)`
  is `True` in Python, so without the guard a stray flag reconciles as the figure
  1 or 0.
- **`_sha` truncates before anything reaches the ledger, because `frank` mirrors
  entries verbatim into shared infrastructure.** The digest proves *which* text
  was replaced to anyone holding the original, without putting the text in
  somebody else's database. The privacy boundary is drawn at the layer that
  crosses the trust boundary, not at the one that is convenient.
- **`_log_seal_event` swallows while `_log_rejection` raises, and the reason is
  written down** — by the time a seal event is logged the pair is already
  committed, so raising would hand the caller a completed write *and* an
  exception. Two error policies in one module, with the distinction recorded, is
  rarer than one applied uniformly.
- **`signing._message` uses a structured JSON encoding rather than a delimiter
  join**, closing the collision where `("ok\x1fadmin", "alice")` and
  `("ok", "admin\x1falice")` sign identical bytes — with the superseded form and
  its failure kept in the docstring rather than deleted.
- **`_rejection_message` tags element 0 with a literal `"rejection"`.** Domain
  separation between two signature protocols sharing a key is the step most
  implementations skip.
