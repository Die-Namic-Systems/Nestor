Inference Analysis

What the Probes Proved That the Corpus Doesn't Say

449 recorded decisions vs. ~200 runtime probe commands

The dogfood decision store holds 449 draft decisions. Roughly 118 touch runtime/product behavior; the rest are dev process. The probes tested actual runtime behavior across every surface. This is what falls in the gap between the two.

Where the Corpus Speaks and the Probes Tested

Three decisions have direct probe evidence. The corpus claims something; the probes checked whether it's true.

Claimed "What happens to an argument the chosen matcher cannot honour?"
Refuse it. Do not accept a number that changes nothing. Decision corpus, exact match

The cascade probe confirmed this: match "Please hold." --abs-tol 5 --pct-tol 0.5 (tolerances on a string matcher) emits an explicit RuntimeWarning naming the ignored flags. The corpus claim holds.

But the probe also found: --abs-tol -1 is silently accepted, falls back to pct-based tolerance, and the JSON still echoes the rejected value under tolerance.abs_tol. The refusal exists for wrong-type arguments but not for wrong-value arguments.

Confirmed, with a gap: type mismatch is refused, value mismatch is silent
Claimed "Is this guard a boundary?"
No, and it says so in its own docstring and refusal message: a tripwire, not a boundary. A PreToolUse hook lives in the agent's own harness… The durable controls are the crypto covenant and the managed-settings layer. Decision corpus, exact match

The decisions probe confirmed this twice: the tripwire fired on NESTOR_SEAL_KEY assignment, and the Claude Code auto-mode classifier independently blocked a reject_match() call with a human verifier name. Two layers, both working, neither one the "boundary."

The internals probe also confirmed the tripwire's blast radius: before_authority.py false-positived on a read-only import sqlite3; SELECT ... because the regex matches column names in SELECT lists. The tripwire is explicitly not a boundary — and the probes showed exactly how its roughness manifests.

Confirmed: the tripwire is a tripwire, not a boundary, and behaves like one
Claimed "Is tooling a gap at all, when Nestor already has a 16-verb CLI and a 7-tool MCP server?"
Yes — the gap is the missing finish, not a missing surface. Present: the nestor CLI, nestor serve (tools/list + call), --json on some verbs. Absent: no --version, no shell completions, --json on some verbs but not all… an MCP server exposing tools only — no resources… Decision corpus, exact match

The MCP probe confirmed every specific claim: 7 tools, no resources, no prompts, no completions. The probe also confirmed the --json inconsistency: --json works on some commands but is silently ignored on others (e.g. ledger verify produces plain text under --json). And --json ask "" breaks the JSON contract entirely (prints a bare ValueError).

The corpus said "the gap is the missing finish." The probes found the finish is indeed missing — and in more places than the corpus enumerated.

Confirmed, and the gap is wider than claimed

Where the Corpus Speaks But the Probes Found Something Different

Contradicted "Should Ask be made to work under --read-only, since it reads like a read?"
No — reverted after reading _ask's own docstring: 'A write endpoint despite reading like a read: a passage is appended to the ledger… An answer served without a trail is the thing Nestor exists to prevent.' Decision corpus, exact match

This decision captures a real design rationale. But the probes revealed a deeper problem the decision doesn't address: ask silently defaults to en→es, making sealed entries in other domains invisible. The decision asked "should ask work under read-only?" and answered no. It never asked "does ask work correctly when it does run?" The domain-scoping silence means ask is serving answers without a trail for a different reason: it's not finding the answer at all.

The rationale holds; the implementation has a different problem the decision doesn't see
Incomplete "What does it mean to validate a matcher at load time?"
Every way the load can fail becomes a refusal naming the spec — not just the one you thought of. Decision corpus, exact match

The edge-cases probe confirmed: bad module specs, missing modules, and failing constructors all produce clean single-line ValueErrors naming the spec. The load path is validated.

But the decision's scope is "at load time." The probes found a different gap: after load, the wrong matcher applied to the wrong domain silently corrupts scores. StringMatcher on a numeric domain scores exact match "412"=="412" as 0.75. No warning, no refusal. The load is validated; the use is not.

Load validation confirmed; runtime domain-matcher mismatch is unguarded

Where the Corpus Is Silent

These behaviors were discovered by the probes. None has a recorded decision, not even a draft. Every nestor decision check returned "no decision on record."

Silent Should --db and --ledger be independent or paired?

Three separate probes hit this independently. The corpus has no decision on it. The behavior directly undermines the audit promise: stats reports "ledger: intact" for a chain belonging to a different store. This is the probe's single most impactful finding, and the corpus is completely silent on it.

Inference: the independence is likely an implementation artifact (two argparse flags, two defaults) rather than a deliberate design choice. No decision was ever made because the question was never asked.

Silent Should a typo'd --db path create an empty database?

SQLite auto-creates on first touch. Nestor inherits this. The corpus has no decision on whether to guard it. The probes showed: a misspelled path produces indistinguishable-from-success output.

Inference: this is an inherited SQLite default that was never surfaced as a design question. The corpus talks about what "nothing sealed here yet" means but never about how a caller distinguishes it from "I'm looking at the wrong file."

Silent Should ask/match default to a specific domain?

The default is en→es, hardcoded in cli.py:domain_args(). The corpus has decisions about what domains are, how matchers bind to domains, and what "near-miss" means. It has nothing about the default scoping.

Inference: the default was set when Nestor was a translation memory only. Entity and numeric domains came later. The default never followed.

Silent Should the keyring validate key length on write?

The probes found: write accepts any hex, read validates and throws. One malformed key poisons the entire file. The corpus has decisions about keyring authority (who can seal, what a revocation means, compromised vs. rotated) but nothing about keyring integrity.

Inference: the keyring design focused on trust semantics (who, not how). The write path was never adversarially tested until now.

Silent Should decision check require a sealed match?

The probes showed: decision check calls an exact match to a pure draft "clear" (exit 0), while match/ask refuse the same row as unverified. The corpus talks about what "clear" means (no rejection, no contradicts edge) but never whether draft-match-clear is the right answer.

Inference: this is intentional ("a CI gate over committed constraints, not a verified-answer server") but the design intent was never written down as a decision. It's code behavior that reads as a deliberate choice but has no record of the deliberation.

Silent Should the UI's ~20 HTTP endpoints appear in --help?

/api/graph, /api/triage, /api/normalize, /api/gate-echo, WebCrypto seal signing — all real, tested, working endpoints. None mentioned in nestor ui --help. The "tooling gap" decision acknowledges "no resources" on MCP but doesn't address the HTTP surface at all.

Silent Should export/import preserve the audit chain?

Import starts a fresh chain from genesis. The source chain is embedded as advisory-only. The probes confirmed this is enforced. But no decision records why — a tool whose mission is "has a human checked this?" deliberately discards the chain proving they did.

Inference: the design choice is sound (a new instance starts its own provenance; replaying someone else's chain is a different trust claim). But it's the kind of choice that should be written down, because the intuitive expectation is the opposite.

Silent Should non-SQLite --db files get a clean error?

The sole path that leaks a raw Python traceback. Every other CLI error is a clean single-line message. The corpus has no decision on error handling conventions at all.

Silent How robust should concurrent writes be?

The probes proved: genuinely robust. 10 simultaneous writers, 20x SIGKILL storm, zero corruption. WAL mode + Nestor's connection handling is solid. But the corpus has no decision about concurrency guarantees at all — this robustness is an unremarked emergent property, not a documented commitment.

The Shape of the Gap

The 449 decisions are predominantly about how Nestor gets built (sessions, hooks, gates, test infrastructure, doc drift, naming conventions). The 118 that touch runtime behavior mostly ask "should X exist?" and "what authority does X carry?" — the ontology of the product.

What the probes tested is different: "given that X exists, does it behave correctly at boundaries?" The gap between the two is operational semantics — the behavior that emerges from the code as written, independently of what any decision says.

The corpus captured why things were built and what authority they carry. The probes found how they actually behave when pushed. The inferential gap is the space between those two questions — and it's where the bugs live.

This is the first time the probes and the decision store have been cross-referenced. The fact that 15+ discovered behaviors have no decision on record doesn't mean they're wrong — some are clearly deliberate (concurrent robustness, export chain non-preservation). It means the decision was never recorded, so the next agent looking at the same behavior will have to rediscover the rationale from the code rather than from the store.
